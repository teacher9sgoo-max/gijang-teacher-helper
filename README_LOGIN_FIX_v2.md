# 로그인이 안 되는 진짜 원인과 수정 내용

전체 코드를 처음부터 끝까지 따라가 보니, 로그인 화면 자체보다 **로그인 화면이 뜨기 전에 실행되는 자동 요청**에서 문제가 시작되고 있었습니다. 아이디/비밀번호 비교 로직(README_LOGIN_FIX.md에서 이미 고치신 부분)은 정상입니다.

## 1) 가장 큰 원인: 로그인 전 자동 요청이 통째로 실패함

`index.html`이 페이지를 열자마자(로그인하기도 전에!) `loadAll()`을 실행하면서, 달력·전달사항·명렬표 등과 함께 아래 두 시트도 **한 번에 묶어서** 서버에 요청하고 있었습니다.

```
'수업 진도', '학생 활동 기록'
```

그런데 `code.js`는 이 두 시트를 학생 개인정보로 보고 `SENSITIVE_READ_SHEETS`에 넣어서, **로그인 정보(아이디/비밀번호)가 없으면 요청 자체를 거부**하게 되어 있습니다. 문제는 이 배치 요청(`sheetReadBatch`)이 "여러 시트를 한 번에" 보내는 구조라서, 이 중 **하나라도 인증이 필요하면 요청 전체가 실패로 처리**된다는 점입니다.

즉, 로그인하기 전인데도

1. 페이지가 열리자마자 서버에 "달력 + 명렬표 + ... + 수업진도 + 학생활동기록"을 한 번에 달라고 요청
2. 서버는 로그인 정보가 비어 있으니 "로그인 확인 실패" 에러로 **전체 요청을 거부**
3. 브라우저는 실패를 감지하고 시트별로 하나씩 다시 요청(안전장치가 있어서 결국 복구는 되지만, 왕복이 2배로 늘어나고 그 사이 로그인 화면이 늦게 뜨거나, 네트워크 상태에 따라 아예 못 뜨는 경우가 생깁니다)

이게 "로그인할 때부터 안 된다"고 느껴지는 가장 큰 이유입니다.

**수정:** `index.html`의 초기 배치 요청 목록에서 `수업 진도`, `학생 활동 기록`을 뺐습니다. 이 두 시트는 어차피 로그인 직후 `syncPersonalRecordsFromServer_()`가 아이디·비밀번호를 실어서 따로(그리고 정상적으로) 다시 불러오므로 화면에는 영향이 없습니다.

## 2) 로그인마다 구글 시트를 통째로 다시 쓰고 있었음

`code.js`의 `accountWithPermissions_()`(모든 로그인 확인이 거치는 함수)가 **아이디·비밀번호를 검사하기도 전에** `ensureTeacherPermissionSheet_()`를 호출하고 있었습니다. 이 함수는 '교사 권한 관리' 시트를 매번 통째로 다시 쓰는(제목행 재작성, 서식 재적용, 기존 내용 지우고 다시 채우기) 무거운 함수입니다.

즉 로그인 성공/실패와 관계없이, **심지어 위 1번의 '로그인 전 자동 요청'에서도** 이 무거운 쓰기 작업이 매번 실행되고 있었습니다. 이러면:

- 로그인 한 번 할 때마다 눈에 띄게 느려지고,
- 여러 선생님이 비슷한 시간에 접속하면 같은 시트를 동시에 덮어쓰면서 충돌·오류가 날 수 있습니다(이 작업에는 `LockService` 잠금도 걸려 있지 않았습니다).

**수정:** 로그인 확인(아이디·비밀번호 비교)을 먼저 하고, 틀리면 시트를 건드리지 않고 바로 실패 처리하도록 순서를 바꿨습니다. 권한 확인은 시트를 다시 만들거나 쓰지 않는 읽기 전용 함수(`readTeacherPermissionRow_`)로 바꿨습니다. 권한 시트를 새로 만들거나 동기화하는 작업은 관리자가 시트 메뉴의 **"교사 권한 관리 시트 만들기·동기화"**를 직접 눌렀을 때만 일어나도록 그대로 남겨뒀습니다.

## 3) 서비스워커(sw.js)가 존재하지 않는 파일을 캐시하려다 계속 실패

`sw.js`가 캐시할 파일 목록에 `./permissions-settings.js`를 넣어놨는데, 실제로는 이 파일의 내용이 `index.html` 안에 합쳐져 있고 별도 파일로는 올리지 않습니다(설치 안내 문서의 업로드 파일 목록에도 없습니다). 서비스워커의 `cache.addAll()`은 목록에 있는 파일이 **하나라도** 없으면 전체가 실패하는 구조라서, 이 서비스워커는 설치가 계속 실패하고 있었을 가능성이 큽니다.

이게 왜 로그인과 관련이 있냐면, 서비스워커 설치가 실패하면 **새 버전으로 교체(activate)가 안 되고, 이미 깔려 있던 옛날 버전이 계속 화면을 가로챕니다.** 옛날 서비스워커가 예전에 캐시해둔 `dashboard-config.js`(로그인 서버 주소가 들어있는 파일)를 계속 보여주고 있었다면, GitHub에서 주소를 새로 고쳐 올려도 사용자 화면에는 반영이 안 되는 상황이 생길 수 있습니다.

**수정:** 존재하지 않는 파일을 목록에서 빼고, `dashboard-config.js`를 정식으로 캐시 목록에 넣었습니다. 캐시 이름도 `v31 → v32`로 올려서, 이번에 배포하면 기존에 어떤 상태였든 새 서비스워커로 확실히 교체되게 했습니다.

## 배포 시 확인해주세요 (코드로 대신 고칠 수 없는 부분)

`index.html` 안에는 예전에 쓰던 것으로 보이는 Apps Script 주소가 3개나 남아 있습니다.

```
WRITE_API_URL        = ...bxucaf195_4iYTZOyTur0N7QMGUUAGoqUquJp26gXRBmqOnCDlABHl-HlIyTB1ibvew...
LEGACY_WRITE_API_URL = ...bxGOJ4oPC2W1qqcger47LhvgDFhVuLLCBxoottOvT09pwp3-wyA91i6Yustckm7IG1Z...
OLDER_WRITE_API_URL  = ...bzCnG_GceglJA6pFfxX5EzEIPEoHvhGK5gyfRHpe4nNNyNATXJi39QEWVOEAL_rC3Uc...
```

이 중 실제로 **지금 배포되어 있는 Apps Script와 정확히 일치하는 주소가 `WRITE_API_URL`(맨 위, 기본값)인지** 꼭 확인해주세요. Apps Script에서 코드를 바꾼 뒤 재배포할 때 **"배포 관리 → 편집(연필 아이콘) → 버전: 새 버전"** 을 사용하면 주소가 그대로 유지되고, **"새 배포"**를 누르면 주소가 완전히 바뀝니다. 지금처럼 오래된 주소가 여러 개 남아 있는 걸 보면, 예전에 "새 배포"로 주소가 바뀐 적이 있는데 `index.html`은 그때그때 새 주소로 갱신됐지만, 예전 주소들이 정리가 안 된 것으로 보입니다.

**적용 순서**

1. Apps Script 프로젝트에서 `Code.gs`를 이번 `code.js` 전체로 교체하고, **"배포 관리 → 편집 → 새 버전"** 으로 재배포(주소 유지).
2. GitHub 저장소 최상위에 `index.html`, `code.js`, `sw.js`를 이번 파일로 교체(Commit).
   - `dashboard-config.js`, `manifest.webmanifest`, `package.json`, `electron-main.cjs`, `preload.cjs`는 이번에 바뀐 내용이 없어서 그대로 두셔도 됩니다(참고용으로 같이 넣어드렸습니다).
3. 웹 화면을 `Ctrl + Shift + R`로 한 번 강력 새로고침 후 로그인 시도.
4. Windows EXE를 쓰신다면 `Actions → Build Windows installer → Run workflow`로 다시 빌드해서 새 EXE를 배포해주세요.
